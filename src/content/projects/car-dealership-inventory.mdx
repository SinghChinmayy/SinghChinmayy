keyDecisions:
  - decision: Atomic conditional UPDATE for purchases
    reasoning: >-
      A purchase decrements stock with a single
      UPDATE ... WHERE quantity > 0 AND deleted_at IS NULL, in the same
      transaction as the insert of a Purchase record with price, make, model,
      and category snapshots. I first built the naive read-then-write version
      and wrote a concurrency test that fires 20 buyers at 5 units — all 20
      succeeded, and the test failed. The atomic version makes exactly 5
      succeed and 15 receive 409, with the history showing both commits.
    alternatives:
      - Read the quantity, check it, then write (races under concurrent buyers)
      - SELECT ... FOR UPDATE row locking (works, but more moving parts)
      - Optimistic locking with a version column and retries
  - decision: Soft delete with audit columns and Stock Adjustment records
    reasoning: >-
      Deleting a listing sets deleted_at and deleted_by instead of removing the
      row, guarded by a check that both are set together. Past purchases still
      point at a real listing, and the deletion itself is attributable. Every
      restock also writes a Stock Adjustment row, so each supported stock change
      is backed by either a Purchase or an adjustment record.
    alternatives:
      - Hard delete (breaks the link from historical purchases)
      - A generic audit-log table (more flexible, but harder to query and test)
  - decision: Test against real PostgreSQL with Testcontainers
    reasoning: >-
      The rules that matter here — conditional updates, check constraints,
      foreign keys with ON DELETE RESTRICT, and pg_trgm similarity — only behave
      correctly in Postgres. Running the 160 backend tests against a disposable
      Postgres container meant the concurrency test was exercising the real
      engine rather than a stand-in.
    alternatives:
      - SQLite in memory (fast, but different locking and no pg_trgm)
      - Mocking the database layer (would not catch the purchase race)
  - decision: pg_trgm word similarity for as-you-type search
    reasoning: >-
      Separate make and model boxes meant typing "Hilux" into Make found
      nothing. A single search box now matches each word against make or model
      in any order and tolerates small typos ("toyta", "nexn"), using pg_trgm
      word similarity with a 0.5 cut-off. No trigram index is added yet; at
      catalogue sizes a sequential scan is fast, and a GIN index is the noted
      scaling follow-up.
    alternatives:
      - Plain ILIKE substring matching (no typo tolerance)
      - An external search service (too much infrastructure for the scope)
  - decision: Migrate Neon first, then deploy to Vercel, from CI only
    reasoning: >-
      On a push to main, CI runs all four checks, then applies Alembic
      migrations over Neon's direct (non-pooled) endpoint, and only then runs
      the production deploy. New code never meets an old schema, and a failed
      check or migration stops the release. The trade-off is that migrations
      must stay backward compatible with the code still serving during them.
    alternatives:
      - Vercel Git integration deploys in parallel with the migration (races)
      - Running migrations during the Vercel build (wrong endpoint, no gate)
  - decision: Rebase-only merges behind a no-bypass ruleset
    reasoning: >-
      Main requires a pull request and four passing checks, with an empty bypass
      list so the rules apply to me too. Merges are rebase-only, because a
      squash merge would fold each failing-test commit and its implementation
      into one and hide the red-green-refactor history.
    alternatives:
      - Squash merges (cleaner log, but loses the TDD evidence)
      - Merge commits (keeps commits, but no linear history)

## Architecture Overview

![Production architecture: the browser loads the React SPA from Vercel's static files and calls the FastAPI Python function at /api/* with a Bearer token; the function uses Neon's pooled endpoint; GitHub Actions runs four checks, migrates through Neon's direct endpoint, then deploys to Vercel.](./_assets/car-dealership-inventory/architecture.svg)

The SPA and the API share one Vercel origin. The API only serves requests and never
changes the schema; migrations run from CI over Neon's direct endpoint, because they
must not go through the transaction pooler.

## What's Built

- **Inventory management**: Administrators add, edit, restock, and soft-delete listings, each with an optional photo and spec sheet
- **Search**: One as-you-type box with multi-word, typo-tolerant matching, plus category and price filters kept in the URL
- **Purchases**: One-unit atomic purchases with price snapshots, a confirmation dialog, and a My purchases history page
- **Auth**: Email and password accounts with 60-minute JWT access tokens and Standard User / Administrator roles
- **Errors**: One error envelope with a request ID for every failure, shared by the backend and the SPA
- **Delivery**: Four required CI checks, rebase-only merges, and a migrate-then-deploy pipeline to Vercel and Neon

## What's Next

- **Refresh tokens**: The access token lives in memory only, so a browser refresh currently requires signing in again
- **Rate limiting**: Login and registration limits need shared infrastructure to work across function instances
- **Indexes for scale**: A `pg_trgm` GIN index for search and a partial index for active listings
- **Administrator audit view**: Surfacing deleted listings and per-listing stock history from the records already stored
