overview: >-
  OpsLens is a design for diagnosing failures in small service environments.
  Given a service and a time window, it should gather evidence from metrics,
  logs, traces, deployments, and dependencies, let a model propose hypotheses and
  read-only diagnostic steps, and produce a report that separates observations,
  hypotheses, conflicting evidence, and unknowns, with every claim citing an
  evidence ID. The harness, not the model, owns scope, permissions, budgets, and
  the audit trail. The backend is planned in Go with REST, PostgreSQL, and a
  worker for investigations. The project started as Aegis, a remediation-first
  platform, and was redirected to diagnosis first on 2026-11-23.
problem: >-
  Operating even a small set of services means piecing together dashboards, logs,
  and traces to answer what changed, what is affected, and what to check next. A
  tool that guesses a cause from timing, or declares a fix without checking, can
  make an incident worse. The design question is how an AI can speed up diagnosis
  while staying inspectable: every claim traceable to evidence, missing telemetry
  treated as unknown rather than healthy, and no ability to change the system it
  is investigating.

approach: >-
  The plan is an investigation lifecycle built around an agent harness. A request
  selects a service, a question, and a time window and returns a stable ID. A
  Go worker runs the investigation with tool, time, and token budgets, loading
  evidence through narrow adapters. A policy gateway validates every tool request
  against scope, arguments, result size, query duration, and budget before
  anything executes, with no shell, arbitrary URL, or database access. The first
  vertical slice uses a recorded evidence bundle and a deterministic baseline
  that produces a cited report with unknowns, before one live telemetry adapter
  and then a bounded model loop are added. Evaluation is built into the same
  repository so quality can be measured instead of assumed.
keyDecisions:
  - decision: Diagnosis first, remediation later
    reasoning: >-
      The project began as a remediation platform. Useful diagnosis has to exist
      before any automated change is trustworthy, so the first release has no
      infrastructure mutation. Human-approved remediation and narrow automatic
      recovery follow only once diagnosis and execution safety have been
      demonstrated.
    alternatives:
      - Remediation-first, as in the original Aegis plan
      - Fully automatic healing from the start
  - decision: The model proposes, the harness decides
    reasoning: >-
      The model suggests hypotheses and diagnostic steps, but the harness
      validates tool requests, enforces permissions and budgets, executes only
      approved read-only queries, and records evidence. Reports must cite evidence
      IDs, and confirmation needs an explicit supporting check, not model
      confidence.
    alternatives:
      - Give the model direct access to shell or query tools
      - Free-text reports with no evidence references
  - decision: Missing data is unknown, not healthy
    reasoning: >-
      Stale or absent telemetry should be visible in the report and should never
      be read as a clean bill of health, which is also why abstaining is treated
      as a valid outcome.
    alternatives:
      - Treat missing signals as no problem
  - decision: Build the evaluator inside OpsLens
    reasoning: >-
      The evaluator, fixtures, scenario catalogue, and replay runner live in the
      same repository, kept separate from investigator logic so expected answers
      never enter model context. It will compare a deterministic runbook selector
      with the AI on identical evidence. ChaosLab remains a separate project, with
      no planned integration or dependency.
    alternatives:
      - Depend on a separate chaos tool for scenarios
      - Judge quality by eye on a few demos
  - decision: Build the backend slice before any UI
    reasoning: >-
      The safety rules and API contract should hold without a presentation
      layer, so a later UI can stay API-facing while the backend owns them.
    alternatives:
      - Start with a dashboard and add the backend later

## Intended flow

The repository describes the investigation experience it is aiming for:

1. Select a service and a time window, or ask a question about an alert.
2. Inspect recent changes and symptoms.
3. Follow a timeline as the AI requests bounded, read-only diagnostics.
4. Read a report that separates observations, hypotheses, conflicting evidence,
   and unknowns.
5. Open the cited evidence and choose the next diagnostic or suggested runbook.
6. Save and replay investigations to evaluate their quality.

This is a design, not an implemented result. I will add an engineering-challenge
section once there is a real one to report.
